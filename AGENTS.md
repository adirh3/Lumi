# Lumi — Agent Guidelines

## Project Summary

Lumi is a cross-platform Avalonia desktop app — a personal agentic assistant that can do anything. It is a chat application with a modern, intuitive UX that feels alive. Lumi's main interface is a chat interface powered by GitHub Copilot SDK as the agentic backend. Single-project solution with MVVM architecture using CommunityToolkit.Mvvm source generators.

## Tech Stack

- **.NET 11** with C# and nullable reference types
- **Avalonia UI 12.1.4** — cross-platform desktop framework
- **CommunityToolkit.Mvvm 8.4** — MVVM source generators (`[ObservableProperty]`, `[RelayCommand]`)
- **GitHub.Copilot.SDK** — agentic backend for LLM interaction
- **StrataTheme** — custom UI component library (external project reference at `../../../Strata/src/StrataTheme/`)

## Core Concepts

- **Chat** — A chat session with Lumi. Primary interaction surface. Has message history and can be linked to a project and/or agent.
- **Project** — Named collection of chats with custom instructions injected into the system prompt.
- **Skill** — Reusable capability definition in markdown (e.g., "Word creator" converts markdown to Word via Python). Listed in system prompt so the LLM knows what's available.
- **Agents** — Custom agent personas combining system prompt, skills, and tools (e.g., "Daily Lumi" checks mail/todos and plans the day). Users create and select them.
- **Memory** — Persistent facts extracted from conversations, included in system prompt across all sessions.
- **Brief** — Lumi's own account of where a project stands (and one across projects), rewritten each night from the day's chats. Memories hold what stays true; the brief holds how things stand now. Every new chat starts with its scope's brief.

## User Flows

- **Onboarding** — A seven-step first run over Lumi's presence (`OnboardingViewModel`, `OnboardingView`): hello (name, pronouns; language and theme in the corner), what Lumi can do (each capability plays as a tiny transcript), how much Lumi may do on its own (Full access preselected, Auto-review, Ask first, each with a live demo; `OnboardingViewModel.Autonomy` sets the default approval mode), the AI account, a consented look at the user's workspace that offers projects to set up (`WorkspaceDiscovery`: git repositories with worktrees folded in, VS Code-family recent folders, folders of recent documents; plus known apps, top sites and recent-file counts, each source opt-in), a short conversation whose answers become memories, and a ready screen with first tasks that open in the right project. One prefetched, tool-free background-model call (`OnboardingPersonalizer`) writes Lumi's first words, tailors the questions and suggests the first tasks; every piece has a deterministic fallback, so onboarding works without an AI. Settings → Profile → Welcome Tour replays it (`MainViewModel.ReplayWelcome` swaps in a fresh `OnboardingViewModel` with `IsReplay`): a replay keeps the language, can be closed at any step, and keeps whatever it already set up. `--onboarding` forces it in Debug, and `--test-onboarding-agent` runs discovery and personalization headlessly on this computer without saving anything.
- **What's new** — Once an installed Lumi has updated, it shows What's new over the window (`WhatsNewViewModel`, `WhatsNewView`, decided by `MainViewModel.WhatsNew.cs` and `WhatsNewSchedule`): the release's spotlight and highlights from `WhatsNewCatalog`, covering every release since the version the user last saw (`UserSettings.LastSeenWhatsNewVersion`; profiles from before it count from 1.0), each with an action that opens where the feature lives (`SettingsViewModel.ShowSetting` scrolls Settings to the row). The phone spotlight is pictured as a phone and, with a phone already paired, says so and opens its settings instead of the setup. Got it, ✕, Escape or a click outside closes it and records the version; new users start at the version they set Lumi up with, development builds neither show nor record it, and Settings → About → What's new opens the latest highlights again. `--whats-new` (or `--whats-new-from X.Y.Z`) previews it in any build without recording anything.
- **Chat** — Streaming chat with tool call visualization, reasoning display, typing indicators. The composer is glass (`StrataChatComposer.glass`) floating over a pane of untinted frost (`ComposerEdgeMaterial`): the conversation column widened by a 48px soft edge (`StrataBackdropBlur.HorizontalFadeLength`), reaching from the island's bottom up to the line where the newest message rests. Untinted frost over the empty canvas looks like the canvas, so scrolling never switches the area on: only history that slides beneath changes, blurring in by position. The pane and the card spend a blur only while `IsContentUnderComposer`. Its + menu (files, recent chats, agents and every other list), the Skills and Connectors buttons and `#` (chats, then files) bring skills, agents and other chats into a message; while the user writes (`:engaged`, which includes its own menus and lists) the composer stays at full size without scaling, the Strata line draws under the text, and the presence behind it brightens (`PresenceController`). Chosen chats are a per-chat composer draft (`ChatViewModel.ChatReferences.cs`) that exactly one message takes (`ChatMessage.ReferencedChats`); their recent transcripts are inlined into the model prompt when it is sent (`ChatReferenceFormatter`), so they work whatever tools the agent allows. Dictation (`ChatViewModel.Voice.cs`, `VoiceInputService`) runs on the device: it asks before the one-time download of the model that suits the computer (`VoiceModelStore`: large-v3-turbo with a dedicated GPU or Apple silicon, small otherwise, plus a Silero speech gate; pinned SHA-256), then listens at once while the model loads; the microphone beside send starts and finishes it, the voice bar shows `VoiceLevel`, `VoicePreview`, `VoiceStatus` and the remembered dictation language (`VoiceLanguageCatalog`, `UserSettings.VoiceLanguage`), Esc/✕ discards (`VoiceCancelCommand`), and sending finishes dictation first so the last words go along. The transcript's scrollbar is the transcript rail (`StrataTranscriptRail`, opted into by `StrataChatShell.ShowsTranscriptRail`; `ChatView.TranscriptRail.cs`): at rest a slim thumb, as every Strata scrollbar rests (their track shows, and their thumb widens, only under the pointer: `ScrollBar.axaml`); hovered, it opens into marks for the user's messages and receipts of the forms they submitted (ticks, previewed as a small copy of their bubble with when they were sent) and for the cards that asked them for something — questions, `ask_input` forms and choices, approvals (dots, previewed as a card with how they were answered) — older ones only in storage too (messages previewed from the outline: `TranscriptHistorySegment.FirstMessageStart`; receipts, questions and forms from `TranscriptHistorySegment.RailInputs`, and from a closed "worked for" row's `TurnSummaryItem.DeferredRailInputs`); the marks near the pointer swell, the nearest is previewed beside the rail (`TranscriptRailMarks`), and a click lands it as Ctrl+↑/↓ do, building its exchange and opening the row that folds it first; dragging the thumb previews the message being passed, and the wheel over the rail scrolls the transcript. Marks are measured (`TranscriptMarksRequested`) only while the rail is open. The rail stacks above the header's and composer's frost, and jumps land a message on the shell's reading line, clear of the header's frost (`StrataChatShell.ReadingLineGap`), so the landed message and its glow read crisply. The floating header holds the chat's state and the composer what the next message can still change: the title pill splits into the chat and a context ring once the chat has context (the ring warms and gives its percentage from 75%, and opens the context card with Compact now); the running pill shows the agents at work while Lumi replies, then everything still running once it is ready, with Stop session (`ShowHeaderRunning`); and a coding chat's git pill splits into its checkout (branch, Local or Worktree, the git card) and what changed (`WorkspaceGit` totals, which open the changes). A new chat's checkout is instead a split chip beside its project on the composer, whose card chooses Local or Worktree; with the first message it moves into the header, since a chat's checkout stays as it started. The project stays on the composer in every chat: choosing another one in a started chat moves the chat there, as Move to Project does (`ChatViewModel.SetProjectId`). While Lumi works, Pause sits beside Stop as a quiet composer tool like the microphone (`StrataChatComposer.SendAccessoryContent`). While it replies, Enter steers the draft into the reply, and Ctrl+Enter or the send button's right-click menu (`StrataChatComposer.QueueCommand`) queues it above the composer instead (`ChatViewModel.QueuedSends.cs`), out of the transcript until the reply finishes and it is sent as the next turn; Alt+↑ selects the queued messages for Enter (steer now), E (edit) and Delete (`ChatView.QueuedSends.cs`). Pause moves queued messages into the durable paused queue. A new reasoning effort picked while Lumi works applies from its next step, but the runtime switches models only between turns, so a model picked mid-reply waits in the session's queue (`SessionModelSwitch`, `ChatRuntimeState.PendingModelSwitch`): the bar above the composer (`ChatViewModel.ModelSwitch.cs`) says it takes over after this reply and offers Switch now, which interrupts the step as Pause does and resumes the same work on the new model (the resumed continuation is labeled with it). A model on another endpoint (Copilot ↔ an account's endpoint) can't join the running session, so it takes over with the next message, without Switch now. An interruption (Stop, Pause, Send now) drops the queued switch, so the chat's pick is applied before the next turn starts, replacing a switch that still waits (`ApplyPendingModelSwitchAsync`, in `SendPauseAwareAsync` and Resume).
- **Memories** — Important info is remembered across sessions via system prompt injection; users review and edit it in Settings → Memories. Two agents keep them: after each reply the memory agent (`MemoryAgentService`) saves what that turn taught, and each night (05:00, or at the first chance after it) the context curator (`Services/Context/ContextCuratorService`) reads the day's chats with a lightweight background-model session per active project, then one across projects. Chats where the user names a project in use (chats of its own in the last two weeks) join its review: one outside projects can start it, one in another project only joins a review that is happening anyway. It rewrites each brief as a few short paragraphs on where the work stands and is heading (the user's plans stay until they happen or change; `update_brief` points out memories a sentence may only repeat), keeps a project brief's starters (up to three of the user's own plans that can start now, phrased as the request that begins them, which the project's new chats offer under For you; never Lumi's own ideas) and repairs, merges and deletes memories with evidence from the chats (`Source = "curator"`, which a user's edit keeps; exempt from the per-turn keyword gate and from maintenance's topic merging; the curator doesn't overwrite a brief the user edits while it works); project curators propose global memories, and only the all-projects curator writes them. Quiet projects are skipped, a missed night is caught up a day at a time (three days on the first run, at most a week), and a failed scope is retried on its own a few hours later. The briefs are a group in Settings → Memories (`BriefsViewModel`), with their own chip beside the categories: in All it lists the brief across projects and the three most recently updated, then Show all; search covers brief text too. There a brief is read, corrected (the curator keeps the user's edits unless newer chats contradict them) or cleared, and Update now reviews the chats without waiting for the night. Each project's page links to its brief. Settings → AI Features → Daily Briefs turns the curator off.
- **Settings** — Profile, Memories, General, Appearance, Chat, Permissions, AI & Models, AI Features, Mobile, Privacy & Data and About, listed in that order under a search box and the user's profile card. AI Features (`SettingsViewModel.AiFeatures.cs`, `AiFeatureViewModel`) is the one place for every way Lumi uses AI on its own — chat titles, follow-up suggestions, automatic memories, daily briefs, Share prompt drafts and the welcome tour: each says when it runs and what it reads, has its switch (features that only run when asked have none) and its model (`UserSettings.AiFeatureModels`, else the default model `BackgroundModel`); a summary turns them all off or on, and it points to the AI set up elsewhere (Auto-review, dictation). AI & Models and Privacy & Data link to it. Permissions sets the default approval mode, rules everywhere or per project, remembered approvals and what unattended work does (see Tool approvals under Key Conventions). Appearance makes Lumi the user's own, and every choice shows at once in its live preview and across the app: the theme (Light, Dark, or System, which follows the computer; picked here or in the welcome tour, the new look spreads across the window from the pick, `ThemeReveal`), an accent palette that recolours buttons, selection, the user's bubbles, the presence glow and Lumi's icon in the app and the tray (`AccentPalettes`, `AppIcon`), the window material (`WindowMaterials`), text size and density, and how brightly the presence glows; Restore default look puts only the look back. Clearing chats or memories and resetting settings confirm in a floating bar.
- **Skills** — Users create skills and reference them from any chat.
- **Phone notifications** — What the desktop notifies about (a finished reply, a question, a form, an approval: `ChatEventHub.PublishAttention`, resolved by `ResolveAttention` once dealt with) reaches paired phones only while the user is away from the PC (`Services/Remote/PhoneNotificationCenter`: locked, or idle for Settings → Mobile's Away after, read by `DesktopPresence`; Debug builds take `LUMI_DEBUG_PRESENCE`). The Android app holds a quiet SSE route (`/lumi/notifications`, pinged every 15 minutes) in Android's remote-messaging foreground service (`LumiNotificationService`), and shows each chat as an Android conversation (`LumiConversations`: a long-lived shortcut per chat, named after it, with its title's initial as its avatar and Lumi as the badge, published before its notification and removed once notifications stop or the PC changes); the web app hands the PC a Web Push subscription (`register_web_push`, keyed by the profile's VAPID key `RemoteWebPushKey`), and the PC pushes straight to the browser's push service (`Services/Remote/WebPush`: RFC 8291 encryption, RFC 8292 signing, only known push-service hosts), so Lumi runs no relay. A tap opens the chat (the service worker focuses the app, or opens `/app/?lumi-chat=<id>`). A finished reply waits up to `PhoneNotificationCenter.SuggestionWait` for its follow-up suggestions (`ChatEventHub.PublishSuggestions`, which also says when none are coming) and carries them (`RemoteNotification.Suggestions`): the Android app offers them as contextual actions beside a free-text Reply (Android 12+; the phone asks to unlock first), which the phone draws as chips and a watch as buttons, since a Galaxy Watch never shows a reply's choices; `setAllowGeneratedReplies(false)` keeps generated replies from crowding them, and `LumiNotificationService` sends the one picked without opening the app; a browser offers the first two as buttons, and the one picked waits in Cache Storage for the opened app to put it in the chat's composer and send it once visible (`MobileShellViewModel.SendFromNotification`), so a suggestion never travels in a URL. While they're on but not allowed, the phone asks again with one tap once a run, or says how to unblock them (`MobileShellViewModel.OfferNotificationsIfUseful`); the web app's test waits for the service worker's `lumi-push-received` receipt to say whether it arrived. A chat on a phone's screen doesn't notify (`RemoteEventHub.IsChatOnPhoneScreen`); one behind the phone's chat list (`RemoteEventSubscription.IsChatCovered`) does. The simulator's `--notifications` runs the real stream and logs what a phone would show.
- **Agents** — Users create agents and select them in the agents tab.
- **Projects** — Chats are organized into projects with custom instructions. Projects are switched from the project switcher at the top of the chat list and set up in Customize → Projects, which the switcher's gears, New project and Manage projects open.
- **Context awareness** — `SystemPromptBuilder` assembles: active project, agent, time of day, user name, skills, and memories (their full text, up to `MemoryTextBudget`; the rest by title). A project chat also starts with the project's brief and a live list of the project's other chats active since it was written; a chat outside projects starts with the brief across projects. The prompt is built once per session, so a nightly brief doesn't break prompt caching.

## UX Principles

- Modern and alive — animated components, responsive interactions, StrataTheme design system.
- Not bloated — main interface focuses on chats with clean navigation. The bar at the bottom of the sidebar has five places — Chats, Library, Jobs, Customize, Settings — and names the open one when the sidebar is wide enough (icons only below that). Every page lights exactly one place: Projects light Customize, Memories lights Settings.
- Welcome experience — the new-chat launchpad (`LaunchpadViewModel`, `LaunchpadStarters.cs`, `ChatView.Launchpad.cs`) is for starting something new: it greets the user for the time of day (in a project, over the first sentence of its brief), offers ideas in tabs and docks the setups on the composer they configure. The tabs are For you, then the starter catalog's categories (`LaunchpadStarterCatalog`: six starters each, 48 in all, with blanks, such as "Plan a trip to [where?]", in every language), always in the same order, so each stays where the user found it. For you leads with the project brief's starters (all three the curator keeps, `ContextBrief.Starters`), then starters the user keeps picking (`AppData.StarterUses`, `LaunchpadStarterUse.Habits`) and starters for the time of day (in a coding project, the code before the hour). The starters keep room for three lines, so switching tabs moves nothing, and the open tab's pill reshapes from the tab it leaves as it slides beneath the others (Strata's `SelectionIndicatorAnimationHelper.MatchSize`). A starter never sends: it fills the composer and selects its first blank, and Tab or the send key walks the rest (Strata's `StrataChatComposer.BeginFillIn`). The setups (starters, to the user) are places: those the user started chats in over the last 30 days (`LaunchpadPlanner.SelectSetups`: project, checkout and agent, never a model, so they start with whatever the default model is then; Just chat is always one), after the ones the user keeps (`AppData.PinnedSetups`, up to `LaunchpadPlanner.MaxKeptSetups`, several per project), which carry a name and line icon of the user's and may keep a model of their own; a kept setup with exactly a learned place's recipe stands in for it (`MergeSetups`), and a hairline sets the learned ones apart. Every kept setup shows, even two kept the same way, and nothing the user gave one is lost: the card and the phone edit a kept setup as itself (`LaunchpadSetupPin.Id`), and an edit that makes it start as another kept setup does absorbs that one only when neither has a name or icon (`LaunchpadSetupKeeper.Edit`). The draft's setup is lit (`IndexOfMatch`: the most specific one that fits, so a model a setup keeps must be the draft's); when none fits, a dashed chip shows where the draft starts, with a pin that keeps it. Setups of one name say what tells them apart (⑂, agent, model or effort: `DescribeTell`). Picking a model in a new chat also makes it the default, so the draft counts as on the default model while its model is the one the chat opened with (`DraftRecipe`). The row is never wider than the composer: the view measures each setup's words (`ChatView.FitLaunchpadRow`, `LaunchpadPlanner.FitRow`: the draft's setup takes a learned one's place, never a kept one's, which hold theirs whatever is lit; without room it stays in the stack, which wears its light) and gathers the rest into a stack of their badges, whose shelf unfolds them above the row and ends with New starter; while everything fits, + ends the row instead. Both open the new starter card: a setup's card for one not kept yet (`LaunchpadStarterEditor.IsNew`), hanging from the row's end, filled from the draft (`RecipeOf`) and never changing it or the default model. Its Starts in turns it to its places, Just chat, the projects (most recently used first, each in the checkout its last chat had: `LaunchpadPlace.StarterSetup`) and the agents; nothing is kept until Add starter, which joins any setup kept the same way rather than renaming it (`LaunchpadSetupKeeper.Add`). A right-click or ⋯ opens a setup's card (`LaunchpadStarterEditor`): a learned one says how often the user starts there and offers Keep, Rename and Don't suggest; a kept one edits its name (one typed and not yet kept goes along with any other change), icon, checkout and model (Default model, or one of its own, listed as the composer's picker lists them, Copilot Fusion once; one no longer offered falls back to the default and says so) and that model's effort (Fusion's tiers among them, `ChatViewModel.ResolveModelQuality`), or removes it. What waits on the user (questions, unread replies) is one quiet capsule at the top right whose card opens those chats; chats in progress stay in the sidebar. One well-known setup Lumi noticed (such as Microsoft 365, from `SetupSuggestionsViewModel`; add new ones to `SetupScenarios`) shows under the ideas. It only observes chats and the store while a chat view is in the new-chat state. The phone shows the same launchpad, touch first (`MobileShellViewModel.Launchpad.cs`, `ChatDetailView`), from what the PC projects (`RemoteProjector.BuildNewChatExperience`: the tabs and their starters, For you and the line under the greeting for no project and up to `MaxLaunchpadScopes` projects, the setups with Just chat among them, the new starter's places, and the chats waiting on the user): the starters are the desktop's glass capsules at touch size, centred line by line (their icons are `RemoteProtocol.LaunchpadIcons` keys), keeping room for the lines the tab needing the most takes at the screen's width (`MobileShellViewModel.LaunchpadStarterTexts`, measured in `ChatDetailView.UpdateStarterRoom`) so switching tabs moves nothing, and Lumi's mark gives way once the welcome would not fit between the bars. The setups row fits the screen as the desktop's fits the composer (`LaunchpadRowFit`, each capsule measured in `ChatDetailView`), the lit one in a learned one's place, never a kept one's (else the stack lights); the rest gather into a stack whose speed dial rises above it over a scrim that leaves only the stack lit, its setups solid cards, the nearest first and New starter last, and while everything fits a round + ends the row. A setup's card, the new starter card and the waiting chats are bottom sheets (hold a setup, or tap ⋯ on the lit one: Keep, Rename or Don't suggest a learned one; the name, icon, checkout, model, effort and Remove of a kept one; the new starter sheet is that sheet for one not kept yet, filled from the draft, its Starts in turning it to its places and Back to its form), and a change waits for the PC's next row and follows the setup there (a kept one by its id, a learned one kept by its recipe). The phone says what it wants rather than toggling: `keep_setup`, `hide_setup` and `retune_setup` name a setup whole (without a model when it starts with the default model; the phone's draft by the model picker's `quality`, empty for a model without efforts, which `ownModel` keeps as the new starter's own even when it is the default model now; a kept one by its `id` too, so a change applies to it as the PC holds it) and go through `LaunchpadSetupKeeper` as the desktop's card does, `keep_setup` with a `name` or `icon` adding the new starter sheet's setup beside any kept the same way, `retune_setup` taking an effort as the picker names it (`toQuality`), and `use_starter` lets For you learn habits from either device. A starter fills the phone's native editor too, since Strata's fill-in selects through the host editor (`IStrataComposerEditor.FocusSelect`); with `AdvancesFillInOnSend` the send button turns to Next blank until every blank has had its turn, then sends. A PC from before the launchpad sends no tabs, and one with the earlier launchpad (`launchpad-v1`) no starter icons: the phone keeps either one's three setups and starters for the hour.
- Transparency — tool calls grouped with friendly names, reasoning tokens displayed, streaming indicators. Transcript work wears Strata's transcript glass: line-icon chips that open into cards, colour only for state, and the Strata line as the sign of work in progress.
- Dedicated management — projects, skills, agents, memories and MCP servers each open on an overview gallery (stats, sort, search, cards) and a full-page editor with a floating save bar. Skills, agents, MCP servers (shown as **Connectors**) and projects are sections of **Customize**, next to **Discover** (plugins from plugin marketplaces, connectors from MCP registries), listed as rows at the top of its sidebar: what is picked or switched while chatting is set up there. Memories is a Settings page (listed under Profile). The chat list's project switcher only switches projects; it shows how many there are, and its gears, New project and Manage projects open Customize → Projects. Hovering a place in the bar or rail moves its icon (bubble pops, books tip, clock sweeps, knobs slide, gear turns), and so does hovering a tool in the chat header (globe tips, screen rises, Workspace panels trade places), unless animations are off in Settings.

## Architecture

```
App.axaml.cs
  ├── DataStore          (settings/index in %AppData%/Lumi/data.json; chats and transcripts in lumi.db, SQLite)
  ├── CopilotService     (GitHub Copilot SDK wrapper)
  └── MainViewModel
        ├── ChatViewModel      → DataStore, CopilotService, SystemPromptBuilder
        ├── SkillsViewModel    → DataStore
        ├── AgentsViewModel    → DataStore
        ├── ProjectsViewModel  → DataStore
        └── SettingsViewModel  → DataStore
```

- **Models** (`src/Lumi/Models/Models.cs`): All domain entities in one file — `Chat`, `ChatMessage`, `Project`, `Skill`, `LumiAgent`, `Memory`, `UserSettings`, `AppData`
- **Services** (`src/Lumi/Services/`): `CopilotService` (SDK wrapper with streaming events), `DataStore` (settings, projects, skills, agents and memories in `%AppData%/Lumi/data.json`; chats and their transcripts in the SQLite chat database `lumi.db` through `Services/Storage`), `SystemPromptBuilder` (composite system prompt)
- **ViewModels** (`src/Lumi/ViewModels/`): `MainViewModel` (root), `ChatViewModel` (streaming chat), `AgentsViewModel`, `ProjectsViewModel`, `SkillsViewModel`, `SettingsViewModel` — all CRUD follows same pattern
- **Views** (`src/Lumi/Views/`): Avalonia XAML + code-behind. `ChatView.axaml` holds the transcript's item templates and styles (tool rows shared with the sub-agent run page live in `App.axaml`); `ChatView.axaml.cs` handles scrolling, layout and interaction
- **External dependency**: StrataTheme UI library referenced as a git submodule at `Strata/` — provides `StrataChatShell`, `StrataChatMessage`, `StrataMarkdown`, `StrataThink`, `StrataAiToolCall`, etc. If a build fails because Strata files are missing, run `git submodule update --init --recursive Strata` from the repo root and retry.

### Key Patterns

- **MVVM** with CommunityToolkit.Mvvm source generators — use `[ObservableProperty]` for bindable properties and `[RelayCommand]` for commands
- **Event-driven streaming** — `CopilotService` events → `Dispatcher.UIThread.Post` → ViewModel state → View reactivity
- **Assistant versus session activity** — `ChatViewModel.IsBusy` / `Chat.IsRunning` describe only the main assistant. Root `assistant.idle` makes it ready even when attached processes or background agents remain active. `IsSessionActive` tracks that independent session lifetime; `HasBackgroundActivity` presents the ready-with-background state. A cached but idle session is not active work.
- **Ownership is not presentation** — session cleanup, eviction, configuration changes and explicit session Stop use runtime ownership (`HasActiveWork`, `OwnsLiveChat`, pending operations), never the assistant spinner. New messages to a ready assistant reuse its session without aborting background work. Child events update their own activity, not the main assistant's busy state.
- **Completion boundaries** — `assistant.turn_end` is a per-step boundary, not readiness. `assistant.idle` settles the main reply; `session.idle` settles all attached work. Keep the existing chat-event `idle` automation contract tied to session completion.
- **Transcript view models** — `TranscriptBuilder` turns `ChatMessageViewModel`s into `TranscriptItem` view models (`TranscriptItems.cs`) grouped into `TranscriptTurn`s; each `TranscriptTurnControl` builds its item views from DataTemplates (`ChatView.axaml`, and `App.axaml` for tool rows the sub-agent run page shares)
- **Persistence** — `data.json` holds everything except chats; chats (metadata rows) and every transcript message live in `lumi.db` (`Services/Storage`: `ChatDatabase` schema and pragmas, `ChatStore` reads, one `ChatStoreWriter` thread for all writes, `ChatStorageJson` message codec). A message's row keeps its JSON body plus indexed columns (role, tool ids, a facet `kind`, text length) so whole-chat features read a few rows through an index instead of the transcript. Search reads the database too: `messages_text`, an FTS5 trigram index (insensitive to case and Latin accents, three characters or more) of what search covers — the user's messages, answers, errors, receipts and form titles, not reasoning or tool output — is kept by triggers on `messages`, so Ctrl+K and `search_chats` (`GlobalSearchService` through `DataStore.FindChatsContaining`, which looks up the query's words as typed, `ChatSearchText.Words`, since the index folds only case and Latin accents) and Ctrl+F (`ChatStore.ReadSearchCandidatesAsync`, which scans the chat's own rows for shorter queries and reasoning) never load transcripts to search them; text not saved yet is searched in memory (`ChatSearchText.Of`).
- **Transcripts load on demand** — `Chat.Messages` holds only a chat's live tail: its newest exchange (from the last user message, with any sends held by Pause after it) plus anything added since. `DataStore.LoadChatMessagesAsync` reads that tail; everything older stays in the database. A new chat has nothing stored, so its tail is all of it. `ChatMessage.StorageSeq` is a message's stored position and `Revision`/`PersistedRevision` make saves incremental (call `MarkChanged()` after mutating a collection inside a message). Messages are appended, removed or truncated, never inserted in the middle. A long session does not keep its tail forever: once the assistant is ready (root `assistant.idle`, and again at `session.idle`) and `ChatViewModel.TailRollThreshold` messages precede the newest exchange, they move to history as reopening the chat would (`DataStore.TryRollTail`), their turns stay on screen owned by `TranscriptHistory` (`AdoptRolledTail`) and the live builder lets go of them (`TranscriptBuilder.ForgetMessages`). While work goes on in the background, an exchange it can still change — a tool call still `InProgress`, such as a background agent, or a shell in `RunningBackgroundShells` — stays live with everything after it, until that work ends.
- **History on screen** — `TranscriptHistory` lays out each older exchange as a placeholder turn (`HistoryPlaceholderItem`) holding its estimated or last measured height. When the viewport reaches one, it is read off the UI thread — its outline from the rows' small columns, then the bodies of what its build shows: everything but the plain steps its runs took, which only a run's page shows (`HistoryExchangeRows`; a run's card still gets the steps that show outside the run, and the one it names as its latest) — built in short slices by a builder seeded with what earlier exchanges showed (`TranscriptSeed`), and swapped in; exchanges the reader left are released again under a budget (`MaxHydratedMessages`/`MaxHydratedSegments`), keeping their turns' measured heights for the next build, and idle cached surfaces release theirs. A swap must not move what the reader sees: the transcript anchors scrolling on the first visible turn whose content is shown (its height is real, not an estimate), never on a placeholder while another turn shows (`TranscriptItemsControl.FindLeadingVisibleContainer`), so an exchange built above or at the top of the viewport is compensated, and content that expands inside a turn straddling the top grows downward; `ScrollingUpThroughStoredHistory_KeepsWhatIsOnScreenInPlace`, `ContinuousScrollWhileTurnsRealize_PreservesVisibleAnchor` and `OpeningWorkInATurnStraddlingTheTop_GrowsDownward` check it. Ctrl+Up/Down stops at placeholders of exchanges that start with a message of the user's own (the outline tells those from a job's wake or a form's receipt: `TranscriptHistorySegment.StartsWithUserMessage`) and builds the exchange before landing on it; the transcript rail marks the same messages and lands them the same way (`ChatView.LandOnUserTurnAsync`). A setting that changes how transcripts are built (tool calls, reasoning, timestamps) releases built exchanges too (`ChatViewModel.RebuildTranscriptAndHistory`). Collapsed "worked for" rows of older exchanges keep only what they show; their steps are built when opened (`TurnSummaryItem.DeferInnerItems`). A background agent can keep working after the user's next message, so its steps span exchanges: a build gives the steps of a run from an earlier exchange to a stand-in for it (`TranscriptSeed.EarlierToolCalls`), and an exchange's runs take the steps they took later before it folds (`ExchangeBuild`'s second builder), exactly as one pass over the whole chat files them. `--history-fidelity` (below) checks that every exchange reads the same built on its own as built whole. A saved plan's card follows the chat's last answer: when the newest exchange went unanswered, the card goes into the newest older exchange with an answer each time that exchange is built (`ChatViewModel.RestorePlanCard`). The newest exchange is built in one pass when a chat opens, so a single enormous exchange still costs its full build then.
- **Whole-chat features use storage** — anything about a whole chat (counts, Workspace rows, the Agents index, in-chat search, fork, share prompt, `read_chat`, `manage_chats` status, the phone's transcript windows and files) reads `DataStore`'s ranged, indexed or counted reads, never `Chat.Messages`. Runs of older exchanges, in the transcript and in the Agents index, keep only what their cards show: a run's steps, their count, its task, log and last text are read when its page opens, and let go when it closes (`TranscriptBuilder.KeepsRunDetailInStorage`, `SubagentToolCallItem.ReleaseDetail`). The Workspace reads its older rows through `ChatStore.ReadOverviewAsync`, so only what the rows show leaves SQLite: runs as summaries (without what only their pages show), answers only when their text could hold a link or they cite sources, and each file edit as the lines it added and removed, counted by SQLite as the transcript counts them (`FileEdits`) — a change to how `ToolDisplayHelper.ExtractAllDiffs` reads edits is made there too (`FileEdits_AreCountedAsTheTranscriptCountsThem` holds them together). The Agents index's steps come without their output, and an older file change's diff reads its edits when it opens (`FileChangeItem.ReadEdits`). Jumps to an older message build its exchange first (`ChatViewModel.EnsureMessageInTranscriptAsync`, `EnsureTurnInTranscriptAsync`); older messages a feature edits are attached (`AttachHistoryMessages`) so saving stores them, so a read that leaves fields out (a summary) must never be attached. Editing or resending an older message cuts the stored history from it (`DataStore.TruncateChatHistoryAsync`) and sends it again as a new message: the edit is made in a copy (`ChatViewModel.EditTargetFor`), so nothing rewrites the stored message, and the chat is reserved against other sends (`TryReserveExternalSend`) from the cut until the new turn starts; an edit that cannot be sent (the cut fails, or another reply is starting) goes back to the composer (`ReturnEditToComposer`). An edit can also undo the agent's file changes since the message: chat sessions track them from their first turn (`EnableFileChangeTracking`); the edit bar offers to undo them, with a Review card listing each file, before anything changes (`ChatViewModel.Rewind.cs`, which reads a session that isn't live through a bare handle, `SessionConfigBuilder.BuildForReadOnlyResume`), judged by the model the edit is sent with — the edited message's own, or one picked while editing — not the chat's last model, since a model of another account starts a new session with nothing to undo, as does a new session already queued for the chat (`EditResumesSession`); and the resend then rewinds the session with them through Copilot's experimental history API (`SessionRewind`) instead of only truncating it, putting files back only for the session and turn the preview read (`RewindFilesPreview.SessionId`, `TurnEventId`). Files the user changed since are kept, and the message sent says what happened to each file until Lumi restarts (`ChatMessage.FileRewind`, never saved). While an edit is open, the edit bar rests on the composer like the paused bar (`#ComposerEditBar`: what sending does, the file offer, Cancel or Esc), the composer is the editor and its send button becomes ✓ Update & resend (Strata's composer `IsEditing`), and every turn after the edited message fades (`TranscriptTurn.IsReplacedByEdit`, set by `ChatViewModel.MarkTurnsReplacedByEdit`, which finds an older exchange that shows only a placeholder by its `StartSeq`).
- **System prompt composition** — `SystemPromptBuilder` assembles context from user name, time of day, agent, project, its brief, skills, and memories

## Localization

Localization changes presentation, not agent behavior or stored user content. See
[the localization guide](docs/development.md#localization) for the catalog layout and display boundaries.

- **Reuse the existing catalogs.** Desktop text uses `src\Lumi\Resources\Strings\en.json` / `he.json` and `Loc`; mobile uses `ChatSessionStrings.resx` / `ChatSessionStrings.he.resx`; shared Strata chrome uses `InteractiveLabels`. Keep English/Hebrew keys and format arguments in sync. Do not introduce another translation framework.
- **Trace consumers before translating a shared string.** A label, description, error or report may also reach a tool result, system prompt, runtime catalog, parser or comparison. Do not assume text is display-only because a user can see it.
- **Keep canonical data separate from UI text.** Preserve skill/agent names and identities, original descriptions, instructions, authored text, file paths, model IDs, status/action/route tokens, hashes and raw streaming text. Built-in defaults may have localized `DisplayDescription` copies; custom or user-edited descriptions stay untouched. Display-only metadata must not be persisted or serialized into runtime payloads.
- **Preserve the model boundary.** Native skill discovery/loading and custom-agent configuration use canonical `Description` / `Content` / `SystemPrompt`, never localized display copies. `LumiFeatureManager` reports are canonical by default; only UI callers opt into `localizeOutput`. System-prompt job descriptions use `BackgroundJobSchedule.Describe(..., localize: false)`. Never temporarily change global language/culture to format one model-facing response.
- **English resource lookup is not UI translation.** `Loc.GetEnglish` deliberately returns the canonical English default regardless of UI language. Do not replace it with culture-dependent `Loc.Get` in persisted defaults or model-facing metadata.
- **Cover every UI branch and host.** Include completed/edited/failed states, empty states, counts/durations, dialogs, tooltips, accessibility names, binding `StringFormat` values, and Markdown code/link controls. Supply the UI language to renderers that do not inherit it; preserve explicitly authored interaction languages and host label overrides.
- **Respect startup and template lifetime.** Resolve shared labels after the saved language is loaded, including deferred templates and crash/startup surfaces. Reuse the existing compiled-binding and startup/restart patterns; do not reset drafts or rebuild runtime sessions just to translate controls.
- **Preserve localization when moving or rebasing UI.** Transfer text and accessibility bindings to the new owning view without restoring deleted controls, retired tools/features or obsolete resource references. Keep upstream command bindings, ownership, layout and motion changes.
- **Verify both sides of the boundary.** Add focused English/Hebrew checks proving that UI labels change while canonical skill catalogs, loaded instructions, tool metadata/results, validation decisions and payload fields do not. Check catalog/placeholder parity and actual populated templates, then use MCP to verify rendered controls, interactions, RTL layout and binding health. A successful build or translated getter alone is not sufficient.

## Focused Engineering

Lumi prefers the smallest complete solution: everything required for the requested behavior to work correctly on supported, realistic paths, without speculative infrastructure or hardening.

### Scope and implementation

- Before editing, identify the requested observable behavior, how it will be verified, and what behavior must remain unchanged.
- Make the smallest coherent change across existing ownership boundaries. Necessary model, service, ViewModel, UI, persistence, and test wiring is in scope; unrelated cleanup or redesign is not.
- Prefer direct code and existing patterns or helpers. Introduce a new abstraction, service, state machine, protocol, compatibility layer, or configuration surface only when it is the most straightforward and cohesive way to satisfy a concrete current requirement, not for hypothetical reuse or future needs.
- Handle the normal-use inputs and failures applicable to the changed path, including empty, missing, first-run, cancellation, and error states, using established repository patterns. Do not add speculative global hardening such as new persistence frameworks, generalized concurrency or merge/version protocols, speculative migrations, retry/rollback frameworks, generalized validation, or unrelated UI/platform infrastructure.
- Do not fix pre-existing issues unless they directly block the requested behavior. Report important unrelated issues separately.
- Before creating a new subsystem, changing behavior outside the requested path, or materially expanding the production implementation, identify the concrete requirement or demonstrated regression that requires it. If the connection is indirect or debatable, keep the smaller in-scope solution and surface the larger change as a follow-up. Ask for approval before expanding; if approval is unavailable, defer it.

### Handling review feedback

- Treat every review finding, whether human, automated, or from a subagent, as a hypothesis. Verify it against the current diff, requested behavior, and a supported realistic scenario before changing code.
- Fix a finding within the current change only when all of the following are true:
  1. It was introduced by the current change, or fixing it is necessary for the requested behavior to work correctly on the changed supported path.
  2. It is high-confidence and reachable in a realistic supported scenario.
  3. Its impact is material, such as incorrect behavior, a crash, data loss, a security issue, a meaningful user-visible regression, or a clear violation of an established repository boundary introduced by the change.
  4. It has a focused fix that does not create a new subsystem or intentionally change behavior outside the requested path.
- Classify findings that fail this gate as separate follow-ups and state why they are outside the current change. Report them, but do not implement them without explicit approval.
- New build failures or existing test failures caused by the current change are always in scope.
- A review-only request, including "review" or "run code review," is read-only. A request to "address the review" authorizes only verified, in-scope findings, not every suggestion.
- Never broaden the implementation merely to obtain an `APPROVE` verdict or eliminate all reviewer comments.
- After accepted fixes, rerun relevant validation. Repeat review only when the fixes materially changed the logic or new evidence warrants it; do not enter recursive review-and-hardening loops.
- Completion is determined by the requested behavior and validation results, not by reviewer silence.

### Proportional validation

- Run the existing builds, tests, and harnesses relevant to the changed surface.
- Add focused tests in the existing relevant test project or harness for the requested behavior, likely regressions, and important boundaries on the changed path.
- If no suitable automated test surface exists, use the existing relevant validation path, such as MCP or focused manual verification, rather than creating generalized test infrastructure solely for the task.
- Do not create combinatorial test matrices, generalized test infrastructure, new harnesses, or platform-wide stress coverage solely for theoretical edge cases.
- Expand validation only when the changed surface, acceptance criteria, or an observed failure justifies it.
- The task is complete when the requested behavior is verified, relevant validation passes, and no known in-scope blocker remains.

For an on-demand Windows desktop memory budget/retention check, run
`pwsh tools\memory\Test-LumiMemory.ps1` (or add `-ProfilePath "$env:APPDATA\Lumi"` to use an online
SQLite copy of the working profile). It builds optimized code with explicitly opted-in diagnostics,
uses isolated data, verifies rendered workload/cache bounds, samples main/child private residency
without forced GC, then runs separate retention checks. `report.txt` is readable; `summary.json`
and `results.json` retain strict completion and raw evidence. Exit 0 is a complete pass, 3 a
completed budget failure, and 1 incomplete/invalid evidence. Never weaken budgets/content to
manufacture a pass or call post-GC/dump residency normal usage. See `tools\memory\README.md`.
The default memory commands now screen one fully populated pass quickly; they retain all
chat/page/history/lifetime/cache/absolute-bloat coverage, not repeated-growth or statistical
claims. Fast must wait for the Library scan and render its item controls before leaving.
For deep memory regressions, use `Test-LumiMemoryRegression.ps1 -Mode Record` once, then explicit
`-Mode Compare`: five fresh calibration processes, archived reference binaries, and interleaved
reference/candidate checks on one hash-verified snapshot. Keep regression and absolute-budget
status separate. Never regenerate the corpus, prepare it in the measured process, silently
reset the baseline, or dismiss GC/residency variance without inspecting the recorded counters.
The separate scheduled/manual `memory-qa.yml` is advisory synthetic Fast coverage, not a new
release/PR dependency or a portable calibration of a developer's private RAM numbers.
Its explicit CI policy uses coarse 1,024 MiB RAM / 2,048 MiB commitment / 200 MiB managed
guardrails; smaller lifetime/cache-count/500 MiB goal findings stay advisory. Incomplete evidence
never passes. Do not silently apply this policy to strict local checks or private profiles.

Two things that used to make agent runs slow or flaky are now handled for you — do not reintroduce the old workarounds:

- **Do not stop `Lumi.Mcp.exe` to unblock a build.** `lumi-mcp` builds and runs from `.mcp-run/` (via `--artifacts-path` in `.vscode/mcp.json`), which is outside `src/Lumi.Mcp/bin`, so a running MCP server can never lock `dotnet build`/`dotnet test` output. Previously the server ran straight out of `bin/`, and Windows locks a running `.exe` exclusively, so any build that refreshed `Lumi.Mcp` failed with `MSB3027`/`MSB3021`. If you still hit a lock, it is a *different* process — check `Get-Process Lumi.Mcp | Select Id, Path` before killing anything, and never kill another worktree's server.
- **Never construct `new CopilotService()` in a test.** Use `TestCopilot.Shared` (`tests/Lumi.Tests/TestCopilot.cs`). Each `CopilotService` owns a real `copilot.exe` child that only dies with the test host, so inline instances used to leave ~41 CLI processes alive at once per run — enough to starve the machine and block the test host itself. The only exceptions are tests that own and dispose their own instance (`CopilotIntegrationTests`, `SuggestionEvalHarness`, `PresentationRoutingEval`).

Tests must never touch the developer's real Lumi data. `TestProfile` (a module initializer in `tests/Lumi.Tests`, and one in `tests/Lumi.Mobile.Tests`) points `LUMI_APPDATA_DIR` and `LUMI_MOBILE_DATA_DIR` at a throwaway folder for the run, so every `DataStore` path — data, chats, skill files, active skills, Copilot sessions, the browser profile, connector caches — is isolated; `TestProfileIsolationTests` pins it. Before it existed, a test whose in-memory store synced its skills replaced every file in the real `%AppData%\Lumi\skills`. Keep it that way: never build test paths from `Environment.SpecialFolder.ApplicationData`, never override `LUMI_APPDATA_DIR` in a test, and give a store that must write skill files its own folder (`new DataStore(data, skillsDirectory)`). An in-memory store never deletes the saved profile's chats (`DeleteAllChatFilesAsync`), and an isolated profile (`DataStore.UsesIsolatedProfile`, also every `lumi_launch` with `appDataDir`) never changes the launch-at-login registration.

Never point it at the live profile.
- `dotnet run --project src\Lumi\Lumi.csproj -- --ui-perf-harness` runs the **UI responsiveness harness**: it measures how laggy the UI feels *from the user's perspective* under a full stress load, then prints a console report and writes JSON ranking the worst UX actions/categories. Details below.
- `LUMI_APPDATA_DIR=<copy of a profile> dotnet run --project src\Lumi\Lumi.csproj -- --history-harness [--history-wait-migration] [--history-chats id,id | --history-top N] [--history-label name] [--history-output path]` runs the **history-scale harness** on a large profile copy (it refuses to run without `LUMI_APPDATA_DIR`): optionally waits for and times the legacy import, then opens the longest chats, scrolls through their whole history and back with a UI-thread latency probe, switches between them and records open time (until the chat shows, and until its first viewport has settled), scroll latency and extents, and post-GC memory per step as JSON. Scroll latency comes from a probe that posts one Background-priority UI-thread job at a time: compare builds by `samplesOver50Ms` and `stallMs` (how often the probe waited more than 50 ms, and how long those waits added up to — a measure of how starved the UI thread was, not a count of visible freezes, since input outranks the probe) together with how far each scroll travelled (`steps` × 0.85 viewport — builds whose height estimates differ travel different distances), since percentiles and shares of samples also depend on how long the run took. Every few steps it lets the viewport settle — what is on screen realized and, where history loads on demand, read and built — so builds compare showing the same content; `settleTimeouts` counts settles that hit their 5-second cap. `LUMI_TRANSCRIPT_DEBUG=1` prints one line per older exchange it builds. Run it on an SSD copy of a real profile; before/after comparisons need the same profile, window size and machine state, and the same chats (`--history-chats`: a legacy index's message counts can be stale, so "the longest" may differ between builds). With `--history-touchpad [--history-gestures N]` it scrolls each chat up and back with touchpad gestures instead of page steps (`TouchpadScroll`: 120 Hz wheel reports raised on the element under the pointer, so every wheel handler runs as for a real touchpad; a steady stroke, then a glide that slows to a stop, then a pause until what it reached shows) and records, for the frames while content moves, dropped and long frames, input delay and how much of the viewport is still empty, and after each gesture how long its content takes to show. Frame figures need Windows to be composing the display: a locked or disconnected session renders about 4 frames a second, and a scroll that stays under 30 frames a second even while content moves is reported as `throttled`. Remote Desktop composes only when something changes, at the rate its client keeps up with (often 30 frames a second), so the frame interval is the usual gap at rest or, if shorter, while content moves; over Remote Desktop compare builds by long frames, input delay, empty viewport and fill time, since smoothness at the monitor's own rate needs the physical console. With `--history-fidelity` it measures nothing and instead checks the target chats (`--history-top 5000` for all of them): each is built whole, in one pass over its messages, and as the surface shows it — every older exchange built on its own with its collapsed rows opened, then the live tail, plus the Agents index rows and the Workspace's rows of older exchanges, which are read from storage — and the two are compared item by item (a run's card by what it shows — its title, latest activity and status — since its steps and their count are on its page; a file change by the lines SQLite counted against those counted from its whole edits); it exits with 3 when any chat reads differently and reports the first differing line. Run it after changing `TranscriptBuilder`, `TranscriptSeed`, `HistoryExchangeRows`, how history is split into exchanges or what the Workspace reads (`ChatStore.ReadOverviewAsync`). With `--history-costs` it measures, instead of scrolling, what each target chat's history costs to hold: the Workspace's rows of its older exchanges (dropped, then read and shown again three times — post-GC memory held, bytes allocated, read and show time) and its largest older exchange built (messages and post-GC memory held, bytes allocated, build time); run it on the same profile for each build being compared. With `--history-verify-migration` (on a fresh copy of a profile from before the database) it waits for the legacy import and compares every chat the legacy index listed with what was stored — its metadata and each message, serialized as the legacy files store it — and exits with 4 when any chat differs; run it after changing `LegacyChatImporter`, the message codec or `ChatMessage`'s persisted fields.

#### UI responsiveness harness (`--ui-perf-harness`)

A DEBUG-only harness that quantifies **UI responsiveness from the user's perspective**. It boots the real headed Avalonia app in an **isolated** appdata dir (your real Lumi data is never touched), seeds ~153 varied scenario chats and 12 projects in memory (tiny → huge, tool-heavy, markdown-heavy), then drives a catalog of real UX actions through the actual ViewModels/Views while a background probe continuously samples **UI-thread dispatcher latency** (at `Background` priority). Navigation, project-switcher and unread-inbox scenarios invoke the actual buttons through Avalonia automation peers; sidebar chat selection exercises the real ListBox handler. Each iteration also arms a dispatcher probe before its action, so short clicks cannot slip between periodic samples. High latency == the UI thread is busy / has little idle headroom == clicks/keystrokes/repaints would feel laggy or frozen. Samples are sliced per-action, aggregated into per-action and per-category stats, classified by impact (Good / Moderate / High / Critical), and ranked worst-first.

- **What it measures (and what it doesn't)**: the probe is a UI-thread **starvation proxy** — it detects when the UI thread is too busy to service work promptly, which correlates strongly with perceived lag and freezes. It does **not** directly measure input-to-pixel or GPU/render-thread time. Treat absolute milliseconds as **relative/regression** signal, not an exact UX latency SLA — especially in Debug builds, where JIT/no-optimization inflates numbers. Use it for ranking, trend tracking, and regression gating.
- **Self-contained & safe**: runs in its own process, seeds its own data in a temp appdata dir, skips onboarding, and **shuts itself down** when finished. It never sends real Copilot messages and never touches other Lumi instances. One failing action is logged and skipped so the remaining scenarios still run; skipped actions, failed measured iterations, zero matched actions, or report-writing failures make the process exit **1**, never a success-shaped partial result.
- **Full mode** (default): runs every UX category — `--ui-perf-harness`.
- **Filtered mode**: limit to specific categories — `--ui-perf-harness --ui-perf-filter navigation,composer` (category names are matched case/separator-insensitively, e.g. `chat-open` == `Chat Open`). Categories: `Navigation` (including Library), `Project selection`, `Unread inbox`, `Chat open`, `Chat switch`, `Transcript scroll`, `Composer`, `Model picker` (opening, reopening, search and scroll), `Chat list`, `New chat`, `Search`. For focused click coverage use `--ui-perf-filter project-selection,unread-inbox,chat-open,chat-list,navigation`.
- **Tuning flags**: `--ui-perf-iterations N` (default 6), `--ui-perf-warmup N` (default 2), `--ui-perf-sample-ms N` (probe interval, default 8), `--ui-perf-settle-ms N` (quiet window, default 120), `--ui-perf-running-chats N` (default 0; simulated concurrent streams, no real messages), `--ui-perf-keep-open` (leave the window open for inspection instead of self-shutdown), `--ui-perf-output <path>` (override JSON path). Aliases for the main flag: `--ui-responsiveness-harness`, `--stress-ui`, `--ui-perf`. Compare before/after runs with identical options, build configuration, window size and background load.
- **Regression gate**: `--ui-perf-fail-on <good|moderate|high|critical>` (aliases `--ui-perf-failon`, `--ui-perf-gate`) makes the process exit **3** if any action's impact is at or above the given level (exit **1** on harness error, **0** otherwise). Use this in CI to fail a build when a UX action regresses past a threshold.
- **Metrics**: latency stats are `p50/p95/p99/max` of probe samples within each action's window. The harness **flushes pending window layout**, drains Loaded callbacks and flushes again before its final Background drain, so incremental changes cannot evade measurement by deferring layout to the next frame. It does not wait for idle/throttled animation ticks or add fixed quiet padding to the measured window. `post(ms)` is the post-action layout/dispatcher settle duration, **not** a pure CPU-time counter. `response95` / JSON `interaction` reports action-start-to-completion-and-settle percentiles separately: it includes awaited drawer animations and I/O and is **not** a UI-stall or input-to-pixel metric. Project selection waits for its auto-opened chat; unread clicks verify the exact reply, filter and read state before finishing. `stall50` / JSON `iterationStalls` is the median per-iteration worst dispatcher stall, alongside raw `iterationMaxMs` and `gen2CollectionsByIteration`, to distinguish recurring lag from outliers/major GC pauses. `UI(KiB)` / `meanUiAllocatedBytes` records allocations on the UI thread in each action window (including concurrent UI work under load). `IterationsWithStall` reports how many iterations hit a High-level stall, a consistency signal.
- **Output**: a console report plus a JSON report at `%TEMP%\Lumi-ui-perf\report-<timestamp>.json` (with a `report-latest.json` copy). The JSON records `runningChats`, `requestedCategories`, `failedActions`, `summary.complete` and failed iteration counts so coverage and load can be checked before comparing timings. It is the authoritative machine-readable artifact; use it to decide which UX section to optimize next. When a gate is set, `summary.gate` carries `{ level, failed, offenders }`; incomplete coverage cannot pass it.
- **Pure-logic core is unit-tested** in `tests/Lumi.Tests` (`UiResponsivenessMetricsTests`, `UiHarnessOptionsTests`, `UiResponsivenessReportTests`). The metrics/options/report types live in `src/Lumi/UiPerf/` and are always compiled; the probe/scenarios/harness are DEBUG-only and excluded from Release builds.


#### What to test and how

- **Did your control actually render?** Use `find_control` to search by name (`#MyControl`) or type (`Button`). If it's not found, something is wrong.
- **Are properties set correctly?** Use `get_control_properties` to check values, visibility, enabled state, dimensions — anything you set in XAML or code-behind.
- **Do bindings work?** Use `get_data_context` to check ViewModel state, and `get_binding_errors` to catch broken bindings. Binding errors are silent failures — always check.
- **Does interaction work?** Use `click_control` to press buttons, `input_text` to type into text fields, `set_property` to change values at runtime. Verify the app responds correctly.
- **Does it look right?** Use `take_screenshot` to capture the window or a specific control. Check layout, alignment, and visual appearance.
- **Is the tree structure correct?** Use `get_visual_tree` or `get_logical_tree` to verify parent-child relationships and nesting.
- **What's focused?** Use `get_focused_element` to check focus behavior after interactions.
- **Styles applied?** Use `get_applied_styles` to inspect CSS classes, pseudo-classes, and style setters on a control.

#### Control identifiers

Many tools take a `controlId` parameter. Three formats work:
- `#Name` — matches by `Name` property (e.g., `#SendButton`)
- `TypeName` — first control of that type (e.g., `TextBox`)
- `TypeName[n]` — nth control of that type, 0-indexed (e.g., `Button[2]`)

#### When to use it

- After adding or modifying any XAML or code-behind UI code
- After changing data bindings or ViewModel properties that affect the UI
- After styling changes — verify pseudo-classes and setters apply
- When debugging layout issues — inspect bounds, margins, and visibility
- When a feature "should work" but you're not sure — take a screenshot and see

## Showing UI Changes to the User

If the feature or fix you implement can be visibly seen by the user (e.g., layout changes, new controls, styling updates, new views), **keep the debug instance of Lumi running** after you finish — do not close it. In your message to the user, explain exactly where they should look to see the change (e.g., "Open the Agents tab and look at the top-right corner" or "Start a new chat and notice the updated welcome panel"). This lets the user immediately verify your work in the live app without having to relaunch it themselves.

### Closing the debug instance when the work is approved

Keep the debug window open only until the user has confirmed the work is done. Once the user signals approval/acceptance of the finished work — explicitly ("looks good", "approved", "we're done") or implicitly by asking for a wrap-up action such as "commit and push", "open a PR", or "merge it" — **close the Lumi debug instance you launched** as part of that final step, before reporting back.

- Close **only your own** debug process, by the specific PID you started (`Stop-Process -Id <your-debug-pid>`). Never close other Lumi windows and never kill the Release/production Lumi process.
- If you launched it through `lumi-mcp` (`lumi_launch`), shut down that same instance (track its PID/instance id from launch, or via `lumi_list_instances`).
- If you started several debug instances during the task, close all of them.
- Mention in your final message that you closed the debug window.
- Do **not** close it earlier — while the task is still in progress, or when you are only reporting intermediate results and awaiting feedback.

## Git Conventions

- **Never run `git stash` (or `git stash pop/apply/drop`) when working from a git worktree.** The stash ref lives in the shared common `.git` directory, so it is global to the repository — a stash created in one worktree is visible to, and can be popped or dropped by, every other worktree and the main checkout. Popping there applies the wrong tree to the wrong branch and silently destroys someone else's uncommitted work. Since agent chats routinely run in isolated worktrees, assume you are in one unless you have verified otherwise (`git rev-parse --git-common-dir` differs from `git rev-parse --git-dir` inside a worktree).
- **Use these instead** when you need a clean tree or want to park changes: commit to your own branch (a WIP commit you amend or reset later), `git worktree add` a fresh worktree, or `git diff > patch` + `git apply` scoped to your directory. Committing is always safe — the stash is not.

## Key Conventions

- **Persistence** — new non-chat data collections go in the `AppData` class in `Models.cs` (saved to `data.json`). Chat data goes through `DataStore`'s transcript API: never assume `Chat.Messages` is the whole chat, and give a new whole-chat feature an indexed read (a `ChatMessageKinds` facet when it needs a kind of step) rather than loading the transcript. Facets are computed when a row is written, so changing `ChatMessageKinds.Classify` — or the `ToolDisplayHelper` tool lists it reads (`IsFileEditTool`, `IsSubagentTool`, ...) — needs a schema upgrade that reclassifies stored rows. A schema change bumps `ChatDatabase.SchemaVersion` (`user_version`) with a migration; one that changes what existing rows mean also raises `min_reader_version`, which older Lumi versions then refuse to open (an addition, such as an index or table, leaves it). What the text index holds is written twice, in SQL for its triggers (`ChatDatabase.SearchTextSql`) and in C# for unsaved text (`ChatSearchText.Of`): change both together (`TextIndex_HoldsWhatChatSearchFindsInMemory` holds them in step), and rebuild the index in a schema upgrade, because stored rows were indexed when they were written. Deletes give their space back to the disk (`auto_vacuum = INCREMENTAL`; `ChatStore.ReclaimFreeSpace` commits once in full mode, since `PRAGMA incremental_vacuum` slows with the square of the freelist). A one-time upgrade (`ChatStore.NeedsUpgrade`: the text index of a schema 1 database, the rewrite of a file from before incremental vacuum) runs while the startup window says so, before any window opens, because every write waits behind it. A damaged database — found at open, or noted while running (`lumi.db.check`, confirmed by `quick_check` at the next start) — is moved aside as `lumi.damaged-<time>.db`, a new one takes its place, and the startup window copies back what still reads (`ChatSalvage`, which skips only rows that do not read or that the new file does not take; `lumi.db.recover` lets a recovery cut short, or put off because the disk has no room for the copy, go on at the next start); a chat that lost messages is marked like a damaged legacy import, so it is never rewound by position, and a chat that fails to open on damage while Lumi runs stays closed with a notification instead of crashing. Profiles from before the database are imported in the background on first start (`LegacyChatImporter`; a chat that is opened or written to first is imported right away): a damaged file keeps what was read before the damage, and one that cannot be read (locked, no access) is `Unreadable` — read again at every start until it can be, while messages added meanwhile are stored from `LegacyChatImporter.UnreadableAppendBase` on, so its transcript then goes in before them. A chat missing legacy messages (`DataStore.IsMissingLegacyMessages`) cannot be edited, because editing rewinds its Copilot session by the positions of its turns, and a copy of it (whole or from one of its messages) replays its transcript instead of forking its session. The old files stay as `chats.pre-sqlite-backup` and `data.pre-sqlite.json`; deleting a chat deletes its file and its entry in that index, and Clear All Chats deletes them all.
- **What's new** — every release Lumi ships has an entry in `WhatsNewCatalog` (an empty one when it brings nothing to show), written before the version bump with the Update Whats New skill (`.github/skills/Update Whats New`): its strings go into all ten catalogs in one step (`Add-WhatsNewStrings.ps1`), its icons are `StrataIcons` names, and a new `WhatsNewDestination` gets its case in `MainViewModel.OpenWhatsNewDestination` (`EveryDestinationLeadsSomewhere` checks it). `WhatsNewScheduleTests.TheCatalogDescribesTheVersionBeingBuilt` fails when `Lumi.csproj` names a version the catalog doesn't reach. Entries of released versions never change.
- **Transcript items** — a new kind of transcript item needs a `TranscriptItem` view model, a case in `TranscriptBuilder`, and a DataTemplate in `ChatView.axaml` (or `App.axaml` when the sub-agent run page shows it too)
- **System prompt assembly** — new context sources should extend `SystemPromptBuilder.Build()`
- **AI features** — a new way Lumi uses AI on its own runs its helper session with `LightweightSessionOptions.Feature` set to a new `AiFeatureIds` id, so it gets the model chosen for it, and gets a row on Settings → AI Features (`SettingsViewModel.CreateAiFeatures`, its `AiFeature_*` strings and its glyph in `AiFeatureIconConverter`); one that runs by itself gets a switch there too
- **Follow-up suggestions are measured on real history** — the chips under a reply (`FollowUpSuggestions`: the reply's beginning and end, the two exchanges before it, and in a project the user's usual replies from `SuggestionHistoryRanker`) were designed by replaying real chats, and a change to their prompt, context or ranking needs a before/after run of `SuggestionEvalHarness` (gated by `LUMI_SUGGESTION_EVAL=1`, model steps also `LUMI_INTEGRATION_TESTS=1`). It opens a profile read-only from `LUMI_SUGGESTION_EVAL_PROFILE`: `BuildCorpus` extracts every moment a reply finished and the user wrote next, `RunEngines` runs engines on a fixed sample (`LUMI_SUGGESTION_EVAL_ENGINES`, default `legacy,current`; `legacy` is the frozen earlier pipeline, `LegacySuggestionPrompt`), and `JudgeAndReport` has the model in `LUMI_SUGGESTION_JUDGE_MODEL` judge whether a chip says what the user actually sent and writes `report.md`. Runs are cached by a fingerprint of the model and the exact question, and judgments per judge, so after a change only what changed runs again; the class comment lists every setting. Two runs of the same engine differ by about a point on 400 decision points and more on a subset, so compare a change against at least two runs of the current engine (rename `runs/current.jsonl` to keep one); a rare situation gets its own sample (`LUMI_SUGGESTION_EVAL_SLICE=unfinished` for replies the work went on after)
- **Presentation routing is measured** — which block an answer uses (`explorer`, `results`, `comparison`, `chart`, `card`, `checklist`, `calculator`, `quiz`, `mermaid` or plain markdown) is decided by the system prompt's presentation guidance (`ResponsePresentationReminder`, the visualization and interactive sections, the research steps), and a change to that guidance needs a before/after run of `PresentationRoutingEval` (gated by `LUMI_ROUTING_EVAL=1` and `LUMI_INTEGRATION_TESTS=1`; cheap by default on `gpt-6-luna`). Each case in `tests/Lumi.Tests/RoutingEval/routing-cases.json` names the blocks an answer may and must not use, and research cases bring their own sources through stand-in `web_search`/`lumi_fetch` tools, so every run sees the same facts and an explorer's links, images and prices can be checked against them. Run it before the change, rename `runs/current.jsonl` to keep it as a baseline (`before.jsonl`, say), make the change and run again: `report.md` sets every kept run beside `current`, with a verdict (explorer use, explorers where they don't belong, cases that pass more or less often), per-category passes and every case's choices. Answers are cached by a fingerprint of the model, prompt and case; run at least two per case (`LUMI_ROUTING_EVAL_RUNS`, default 2) since a model's choices vary; the class comment lists every setting
- **Tool display names and icons** — add friendly mappings in `ToolDisplayHelper.GetFriendlyToolDisplay()`, the live status wording in `ToolDisplayHelper.FormatToolStatusName()`, and the tool's line icon in `ToolDisplayHelper.GetToolIconKey()` (keys live in `TranscriptIcons`; `TranscriptIconConverter` maps them to `StrataIcons`). A shell command or query is named by the purpose the agent gave it (its `description`, `ToolDisplayHelper.GetCommandTitle`), a tool Lumi has no wording for by the SDK's tool title or MCP tool name (`GetToolTitle`), and a running tool's `tool.execution_progress` message replaces its glance detail while it runs (`TranscriptBuilder.UpdateToolProgress`)
- **Live progress from the SDK** — the agent's plan in its SQL todos is read back on every root `session.todos_changed` (`session.Rpc.Plan.ReadSqlTodosWithDependenciesAsync`) and kept on the `sql` call that changed it (`ChatMessage.PlanSnapshot`, scoped to the turn by `ToolDisplayHelper.BuildSqlPlanSnapshot`), so that call shows as a plan update like `update_todo`. A file tool whose arguments are still streaming (`assistant.tool_call_delta`) shows as a temporary "Writing notes.md" row (`StreamingToolCall`, `TranscriptBuilder.ShowToolDraft`) until it starts. Live shell output comes from `tool.shell_output` chunks (`LiveShellOutput` keeps the latest 16 KB of a long one); the deprecated `tool.execution_partial_result` is only a fallback
- **Tool approvals** — Copilot enforces them; Lumi only chooses its native controls (`Services/Permissions/ApprovalPolicy`): Full access / Auto-review / Ask first are the native `allow-all` / `assisted` / `manual` modes (`assisted` needs the runtime's experimental `AUTO_APPROVAL` flag, which `CopilotService.ApplyAutoReviewFeature` turns on; with Use only your own accounts it maps to `manual`, because the reviewer is a Copilot request), Allow and Never rules are native session rules, and Always-ask rules are the native managed-settings Ask layer (startup-only, so a changed one rebuilds the session). `ChatViewModel.Permissions.cs` installs the chat's mode and rules on every create and resume (`PrepareSessionPermissionsAsync`; the runtime keeps neither across a resume) and on every live change, clearing the session's own "Allow for this chat" approvals first because each is also saved as a rule (so Forget works in an open chat); it shows requests that need a person as cards in the owning chat; `PresentPermissionRequest` takes the native answer as a `NativeApprovalDecider`, which is the seam tests use. A new Lumi tool must be classified in `ApprovalPolicy`: harmless (only looks or talks to the user, so it carries native `skip_permission`) or a member of a group the rule builder offers. Approval decides whether an action runs, not what it can reach: only a project's sandbox (below) limits what commands reach
- **Sandbox** — projects can have Copilot run their chats' commands in the runtime's OS sandbox (MXC; `SessionConfigBase.SandboxConfig`, experimental `GHCP001`). Like approval modes it cascades: `UserSettings.Sandbox` (`SandboxSettings`: Settings → Permissions → Sandbox, `SettingsViewModel.Sandbox.cs`) is the default, `ProjectSandbox` (Customize → Projects → Sandbox) overrides `Enabled` and `AllowInternet` when non-null, and folders add up (yours, the project's, the chat's; Blocked wins). `SandboxPolicy.IsOnFor` is the one answer to "is this project's chat sandboxed": the project's choice, else your default for a project with a folder; chats outside projects run in the home folder and are never sandboxed. `SandboxPolicy.Build` turns that plus the chat's `SandboxDisabled` and `SandboxFolders` into the policy; `ChatViewModel.Sandbox.cs` sends it with every create and resume (`PrepareSessionSandboxAsync`; the runtime keeps none of it across a resume), catches a just-published session up with changes made while it started (`CatchUpSessionSandboxAsync`, after each `TryPublishSession`), and applies a change to a live session through `session.Rpc.Options.UpdateAsync` (`ApplySandboxPolicyAsync`, only when `SandboxPolicy.Describe` changed; a Settings or project change reaches live chats through `ApprovalPolicyChanged`, and a chat moved to another project, open or running in the background, takes that project's approvals and sandbox at once through `ApplyPoliciesToLiveSession`). A sandboxed project's chats never use the connector proxy (`BuildMcpPlan`), which would start local connectors in Lumi's own process, out of the sandbox's reach; a session that started with it is rebuilt once the sandbox applies to it, and one still working is cut off from its proxied connectors until then (every session reaches the proxy as a client of its own, `McpProxyRuntime.AcquireSessionRegistration`, so releasing its lease revokes only that session). With no sandbox Lumi sends nothing, so an organization's managed policy still applies. `AllowBypass` is on because every escape reaches a person, even in Full access: `SandboxEscape.Of` reads it from the full request (file reads and writes carry it only there; for a request a resumed session still waits on, `SandboxEscape.OfPending` finds it in the session's history, and a session whose history can't show it isn't restored), the card answers through `session.Rpc.Sandbox` (`NativeSandboxDecider`: grant the path, or turn the sandbox off for the chat), Allow all leaves escapes alone, and an allowed folder is saved to the chat or the project (`SandboxPolicy.Remember`). Host support (`SandboxHostState`, from `CopilotService.GetSandboxHostSupportAsync`) gates both pages' switches; their folder rows share `SandboxFolderRow` and its template in `App.axaml`. Local network stays on, since on Windows name resolution and the credential proxy need it, and the runtime always lets sandboxed commands write the temp folder, so a fixture a test expects blocked lives outside it. Lumi's own tools (browser, desktop control, web fetch) run in Lumi's process and are never sandboxed: never say they are
- **Embedded apps** — an MCP App or Copilot canvas is an `EmbeddedApp` on the tool message that opened it (a canvas on its `open_canvas` call; `Services/EmbeddedApps/EmbeddedAppData`), and one `EmbeddedAppItem` is both its transcript card and its Workspace row. A chat's app messages, older exchanges' included, are in memory while it is loaded (read with its tail through the `app` facet and kept attached): the app list, canvases and the model's app context read them through `DataStore.GetAppMessages`, never `Chat.Messages`, and a change made to an `EmbeddedApp` in place is saved only after `MarkChanged()` on its message. Only identity and the tool exchange are saved; HTML, resource metadata and canvas URLs come from the chat's session when the app opens (`ChatViewModel.PrepareAppAsync`, which resumes the session if needed). The Workspace's app page (`EmbeddedAppView`) loads each app from a loopback `EmbeddedAppHost` (host and sandbox origins, a random path secret) and shows Lumi's loading and error states until the bridge reports it ready; a failed bridge request goes back to the app, only a failed start reaches the page. The bridge source is `tools/EmbeddedApps` (`npm run build` regenerates `Assets/EmbeddedApps`), and Lumi's theme reaches apps as the standard MCP Apps host style variables
- **Image generation** — the model always sees one `image_generation` tool (`Services/ImageGeneration`): Copilot's native tool (`SessionConfig.ImageGeneration`, set explicitly on every create and resume) whenever Copilot is signed in and allowed, whatever model the chat uses, else `AccountImageGenerationTool`, which copies the native tool's name, description and schema and calls the user's OpenAI Images API account (`ImageGenerationRouting` decides). Never add image-use guidance to the system prompt: when to create images is the tool description's job, and how to show them comes after each image through the `OnPostToolUse` hook (`GeneratedImageResults.BuildPresentationGuidance`), so the model shows an image by putting it in its reply and leaves out images made for other work. Saved paths live on the step (`ChatMessage.GeneratedImages`, the `image` facet), which the transcript, Library and phone read.
- **Explorer pictures on phones** — a phone never reads the pages an answer links to: the app sets `StrataInteractiveBlock.ExplorerPictureLoader`, which asks the PC (`RemoteProtocol.Routes.ExplorerPicture`, capability `explorer-pictures-v1`) for an option's picture by chat, message, block and option id, never by address. The PC serves the option's own image (a web picture through Strata's guarded client, or a local one the chat made showable, as markdown images are) or else its link's preview while `ShowsLinkPreviews` is on.
- **Connectors naming** — user-facing text calls MCP servers **connectors** ("Connectors" in Customize, Discover, Settings, chips and the phone app). Keep "MCP" for the protocol, `mcpServers` config files, MCP registries and LLM-facing tool descriptions; code, `Mcp*` types, page index 6 and automation IDs such as `#CustomizeMcpTab` keep their names.
- **Agents naming** — user-facing text calls custom personas **agents** ("Agents" in Customize, search, Discover and the phone app); built-in agents keep their names ("Coding Lumi"), and "Lumi" still names the app, Lumi packs, Lumi codes and Lumi tools. LLM-facing text (`manage_lumis`), code (`LumiAgent`, `Lumis_*` keys, `LibrarySection.Lumis`), page index 4 and automation IDs such as `#CustomizeLumisTab` keep their names.
- **Tooltips** — Strata's `ToolTip` theme is click-through, so a tip can never swallow a click. Lumi's overlay tips default to pointer placement (+20px, and near a window edge they flip or slide onto the cursor); give controls at an edge, in rows or in moving layouts a control-relative `ToolTip.Placement` with an offset that clears them, and don't repeat a visible label in a tip.
- **Management pages** (Projects, Skills, Agents, Memories, MCP) share one pattern — `SelectedX`, `IsEditing`, `EditX` properties, card collections for the overview, `HasUnsavedChanges`/`ShowSaveBar`, `Save` (keeps the item open), `DiscardChanges`, `RequestDelete`/`ConfirmDelete`, `CloseDetail`. Views reuse `Views/Management/ManagementStyles.axaml` and take their colour from one `Hue.*.axaml`; sidebars (Projects, Skills, Agents, MCP) bind `SelectedItem` one way and open items through `OnManagementListSelectionChanged`. Each overview and detail surface sets `ManagementMotion.Entrance` (and `ManagementMotion.Key` to the item it shows), so the sections of its scrolling content rise in on the render thread when it appears or moves to another item — a UI-thread transition would already be over by the time a page finishes building. The Jobs page wears the same overview and editor (`Hue.Job`, `BackgroundJobsViewModel.Overview.cs`/`.Editor.cs`): it opens on its overview, grouped by state (running now, needs attention, enabled, paused), and opens a job only when asked (a click, search, or a job's wake); its sidebar keeps a two-way `SelectedVisibleJob` binding, and a refresh keeps unsaved edits
- **Management UI lifetime** — `MainWindow` builds only the active management, Jobs, Library or Discover view. Leaving releases its bindings and content while still attached (`ManagementPage.Release`), but keeps the ViewModel, drafts, selections and filters. Sidebar panels receive their ViewModel only while active, so hidden lists release their generated rows. Scroll offsets are restored only for the same item/filter state; snapshots contain offsets and state keys, never controls. Do not prewarm pages on navigation hover or keep visited view trees cached.
- **Settings pages** keep Strata's `StrataSettingGroup`/`StrataSetting`, re-templated for Settings by `Views/Settings/SettingsStyles.axaml` into the management pages' cards, insets and rows, so search, highlighting and revert-to-default (`Is<X>Modified` + `Revert<X>`) keep working. A card's header icon is `st:SettingsChrome.Icon`; other words that should find a row, or a panel that isn't a setting, go in `st:SettingsChrome.SearchText`. Search (`SettingsSearch`) matches a name by the start of its words, a query typed without spaces or one typo, and a description only by the start of its words. A new persisted setting also needs its line in `AppDataSnapshotFactory`, which copies settings field by field, and a look-and-feel one belongs in `ResetAppearance` and `IsAppearanceCustomized`. An accent palette is one merged dictionary of `Application.Resources`, swapped whole. Lumi's icon is drawn by `AppIconArt`: inside the app it is the `Image.LumiMark` resource, which `AccentPalettes.Apply` redraws in the accent (show it with `{DynamicResource Image.LumiMark}`, never the PNG), and `App.RefreshTrayIcon` redraws the tray. Installed icons stay in Lumi's colours and are rewritten with the Debug `--write-app-icons`; never edit them by hand. AI accounts (Settings → AI & Models) is the one place for model providers: the guided `EasyConnectView` and, in the same card, **Use only your own accounts** (`UseBYOKOnly`) and **Endpoints & models** (`#AdvancedByokSettings`), which edits the same `ByokEndpoints`/`ByokModels` by hand. User-facing text says accounts; "BYOK" stays in code and search keywords
- **Customize and Discover** — skills, agents and MCP servers that plugins install or that live in the Copilot folder are read-only in their section: each page's `External` (`ExternalCapabilitiesViewModel`) is fed from the chats' capability catalog (`CapabilitySnapshot.External`) and shown by `ExternalCapabilitySections`/`ExternalCapabilityDetail`; edits go through "Make a copy" (`ExternalCapabilityCopier`). Plugins install through the SDK plugin RPCs (`PluginCatalogService`), never by writing into `~/.copilot` directly; after a change call `CopilotService.NotifyPluginsChanged()`. Lumi sessions use their own config directory, so installed plugins reach chats only through `SessionPluginRoots` → `SessionConfigBase.PluginDirectories`. Registry MCP servers become ordinary Lumi `McpServer`s tagged with `CatalogId`
- **Avalonia list pitfalls** — Avalonia 12 crashes (`Target control is not attached to the visual tree`) when a tooltip closes after its control left the tree, so don't put `ToolTip.Tip` on items of collections that are replaced or refiltered while the pointer may rest on them, and update such collections in place rather than clearing them. Large galleries build their items a page at a time across frames (see `DiscoverViewModel.SyncGrid`); schedule that work with a short `DispatcherTimer.RunOnce(..., DispatcherPriority.Normal)`, because `Background`/`Input` priority jobs wait while Windows reports pending input, such as during scrolling
- **Strata controls** — always use Strata UI components for chat elements. Inspect the StrataTheme source for API
- **Style ownership** — gate component-only helper rules by a static owner or named part instead of letting every control of the same type retain inactive class-style setters and bindings. Keep existing class/pseudo-class conditions and rule order to preserve priority and dynamic states; popup children may need their own root scope, the collapsed rail is separate from the sidebar, and launchpad setups live above the composer rather than in `WelcomePanel`. Shared utilities such as diff-stat colors serve several surfaces, including flyouts. Type selectors follow `StyleKeyOverride`, not necessarily the runtime type (`TranscriptItemsControl` uses `ItemsControl`); a named owner avoids that mismatch. Do not remove currently inactive styles as a memory optimization.
- **Modify StrataTheme when needed** — if a UI change makes more sense as a StrataTheme feature or fix (new control, new property, style tweak, bug fix), go ahead and make the change directly in the `Strata/` submodule. Don't work around library limitations in Lumi when the right fix belongs in Strata.
- **No over-engineering** — this is a personal app, keep implementations simple and direct

## Cross-Platform Conventions (Windows / Linux / macOS)

Lumi targets `net*-windows` on Windows and `net11.0` on Linux/macOS (the csproj selects the TFM by host OS). The `WINDOWS` preprocessor symbol is defined **only** for the Windows TFM, so it is the discriminator for compile-time gating. When adding a feature that touches platform-specific APIs, follow these rules so Windows-only capabilities never break the build — or leak to the agent — on Linux/macOS:

- **Compile-gate Windows-only TYPES with `#if WINDOWS`.** If code references a type that only exists on the Windows TFM or a Windows-only package (WinRT `Windows.*`, `FlaUI`, `Microsoft.Web.WebView2`, `Microsoft.Toolkit.Uwp.Notifications`), keep it inside `#if WINDOWS`. Where no native implementation exists, provide an `#else` stub with the **identical public API** so cross-platform callers compile unchanged. Examples: `UIAutomationService`, `NotificationService` (toast). Voice uses shared SDL/Whisper implementations; the browser and cookie services also have real Linux/macOS implementations. Do not replace them with unsupported stubs.
- **Runtime-gate Windows-only BEHAVIOR with `OperatingSystem.IsWindows()`** when the types compile everywhere but only work on Windows (P/Invoke, `System.Drawing`, registry). Provide a real Linux/macOS branch where one exists (e.g. notifications use `notify-send`/`osascript`; autostart uses `.desktop`/`.plist`; shells use `bash`/`pwsh`). Examples: `FileIconHelper`, `GlobalHotkeyService`, `MainWindow.ApplyLaunchAtStartup`, `BackgroundJobService`.
- **Condition Windows-only NuGet packages** in `Lumi.csproj` on the TARGET platform of the TFM (not the host), e.g. `Condition="'$([MSBuild]::GetTargetPlatformIdentifier($(TargetFramework)))' == 'windows'"`.
- **Do NOT leak unusable capabilities to the agent.** Gate platform-dependent features consistently in *three* places:
  1. **Tools** — register Windows-only `ui_*` tools behind `OperatingSystem.IsWindows()` in `ChatViewModel.BuildCustomTools`. Browser tools instead use `NativeBrowserLogic.IsEmbeddedBrowserAvailable`.
  2. **System prompt** — `SystemPromptBuilder.Build` is parameterized by `PromptPlatform`; reserve PowerShell/COM/winget/registry/desktop UI-automation guidance for Windows. Describe the supported native browser on Linux/macOS with its actual limits, not Windows-only options.
  3. **UI** — hide unavailable affordances through the same capability policy. Voice follows `VoiceInputService.IsAvailable` on Windows/Linux/macOS; global hotkeys remain Windows-only. Browser Settings and the agent tool picker follow `NativeBrowserLogic.IsEmbeddedBrowserAvailable`. Prefer a Strata property over hard-coding control visibility in Lumi.
- **Keyboard shortcuts must feel native per platform.** Handlers compare against the platform command modifier — Cmd (`KeyModifiers.Meta`) on macOS, Ctrl (`KeyModifiers.Control`) on Windows/Linux — so a single check stays correct everywhere (on Windows/Linux it is exactly the old `Control` check). Shortcut HINT text is adapted centrally by `Loc.AdaptKeyboardHint` (applied inside `Loc.Get`), which renders ⌘/⌥/⇧ on macOS only; for hints built outside the localization table (typed `Loc.*` properties, literal XAML), call `Loc.AdaptKeyboardHint` explicitly.
- **Keep `[SupportedOSPlatform("windows")]`** on Windows-only members to satisfy the CA1416 platform-compatibility analyzer.
- **Validate cross-platform changes:** build on Linux (WSL: `dotnet build src/Lumi/Lumi.csproj -c Debug` from a Linux host produces the `net11.0` TFM) and run the OS-aware prompt tests (`SystemPromptBuilderTests`, which assert no Windows-only leakage on Linux/macOS). CI (`pr-validation.yml`) builds on `windows-latest` (+ tests), `ubuntu-latest`, and `macos-latest`.

### Embedded browser maintenance

Keep the two browser engines independent; share the existing DOM automation and engine-independent result/operation contracts rather than introducing a new engine abstraction for feature parity.

- **Windows ownership:** `BrowserService.cs`, `BrowserService.Automation.cs`, and `BrowserService.Tabs.cs` own WebView2. Preserve Windows tool descriptions, parameter metadata, and prompt wording when changing native behavior.
- **Native ownership:** `BrowserService.Native.cs` coordinates profiles, tabs, and window hosts. `NativeBrowserTab.cs` owns each view's lifetime; its `Automation` and `Upload` partials own actions and file attachment. Native dependencies are conditioned on the target TFM, not the build host.
- **Capability policy:** `NativeBrowserLogic.IsEmbeddedBrowserAvailable` is shared by tool registration, the agent picker, Settings, and prompt construction. Native macOS requires 14+ for isolated persistent profiles. Initialization must remain consistent with that policy.
- **Layout and lifetime:** native views live in each window's `NativeWebViewLayer`, outside `UiScaleHost`. Keep view access on the UI thread, use `BeginReparenting` for host transfers, and preserve the physical-bounds/page-zoom conversion. Closing a host must release its registration without disposing a browser transferred to another window.
- **Cookies:** explicit import/reset acts on initialized tabs in the same normalized Lumi profile using the existing weak service registry. Do not initialize unopened peers or introduce continuous session copying. Linux session cookies remain per-tab; authenticated flows should stay in one tab.
- **Native interop:** `NativeWebViewPlatform.cs` handles capture/zoom and `NativeWebViewCookies.cs` handles cookie transport. Check the pinned Avalonia WebView package's source before changing handle, callback, or store assumptions; retain typed handles and native completion/release ownership.
- **Readiness:** document readiness is not application-effect completion. Keep bounded target waits, coordinated-field validation, fail-stop batches, and navigation guards. Do not reintroduce fixed settling delays on already-ready actions; use explicit expected-state waits for delayed page effects.
- **Intentional differences:** native popups lack `window.opener`, embedded downloads are Windows-only, and native JavaScript is synchronous without Windows diagnostics/timeout parameters. These limits are documented in the [README](README.md#embedded-browser); full parity is not a cleanup requirement.

For browser changes, run the existing Debug `--test-browser-native` fixture with isolated data and a loopback server, plus the focused `NativeBrowser*`, `NativeWebViewPlatformTests`, `BrowserPlatformWiringTests`, and browser prompt/tool tests. Run `BrowserServiceIntegrationTests` in a fresh Windows test process for WebView2 regression coverage. The [README](README.md#embedded-browser) documents fixture flags and system dependencies.

Use headed JSON/PNG results to verify real pixels, bounds, host transfers, cookie profile scope, uploads, and navigation safety; a successful build alone does not establish native support. The dedicated `browser-native-validation.yml` workflow covers Linux and both Intel/Apple Silicon macOS hosts as well as Windows. Compare `operationTimings` on the same host/configuration when investigating latency; they are fixture tool-completion timings, not input-to-pixel measurements or a universal website SLA.
